## Overview

The changelog consists of released versions and the `tip` section, which holds changes that are merged but not released yet.
Most changes go to the `tip` section. Occasionally, entries in released versions are refined, or a missing entry is added to a released version.

Changelog files match the pattern `docs/**/CHANGELOG[_YYYY].md`. `CHANGELOG.md` holds the current year, and `CHANGELOG_YYYY.md` files hold previous years.
The `CHANGELOG_YYYY.md` file for the current year only includes `CHANGELOG.md` via the `{{% content "CHANGELOG.md" %}}` shortcode. Edit `CHANGELOG.md`, never the current year's file.
The current `CHANGELOG.md` starts with a header containing a short description and useful links. Keep it intact.

Ignore files in the `vmdocs` directory. It is generated by `make docs-debug` for running the whole docs site locally, and changes there can't be committed.

## Review workflow

1. Ask the user which base to compare against and whether the change is by an external contributor, unless they already said. Ask in three `AskUserQuestion` calls, one after another:
   1. Remote: `origin`, `opensource`, `enterprise`. The user can also type the whole `<remote>/<branch>`; then skip the branch question.
   2. Base branch: offer only branches that exist on the chosen remote (`git branch -r --list '<remote>/*'`), from `main`, `master`, `cluster`, `enterprise-single-node`, `enterprise-cluster`.
   3. External contributor: `no`, or `yes` with their GitHub username typed in.

   The base is `<remote>/<branch>`.
   Don't guess whether the change is by an external contributor; the answer decides the thanks sentence and whether an entry is expected.
2. Collect the changelog changes: `git diff <base>...HEAD -- 'docs/**/CHANGELOG*.md'` plus uncommitted changes.
3. Read the code changes: `git diff <base>...HEAD` plus uncommitted changes.
4. Check that each changed entry matches the actual code change: the type, the affected components, flag/metric/API names, default values, and the described behavior. Flag claims the code doesn't support and user-visible changes the entry leaves out.
   If the code change is user-visible (or by an external contributor) and there is no entry, report it.
5. Check each changed entry against the rules below.
6. Report every problem with a corrected line. Say nothing about entries that are fine.

## Write workflow

1. Ask the user which base to compare against and whether the change is by an external contributor, the same way as in step 1 of the [review workflow](#review-workflow).
2. Read the code changes: `git diff <base>...HEAD` plus uncommitted changes.
3. Decide whether the change belongs in the changelog (see [What belongs in the changelog](#what-belongs-in-the-changelog)), and pick the type: security, feature, bugfix or update note.
4. Find the affected [components or features](#components-or-features) and the related issue/PR. If the issue/PR can't be found, ask the user.
5. Add the entry to the right group in `tip` of `CHANGELOG.md`, or update the existing entry for the same change.
6. Check the new entry against the [review workflow](#review-workflow) steps 4–5.

## What belongs in the changelog

- Changes visible to end users must be in the changelog: new functionality, fixed bugs, security fixes, changed behavior, flags, metrics or APIs.
- Code changes by external contributors are usually reflected in the changelog to credit them, even if they aren't visible to end users, e.g. refactoring or tests. The maintainer who merges the change makes the final decision.
- Refactoring, chores, tests and other changes invisible to end users can be omitted from the changelog when they are done by the team.

## Tip section

The `tip` section follows this pattern:

```md
## tip

**Update Note 1:** xxx

* SECURITY: xxx
* SECURITY: yyy

* FEATURE: xxx
* FEATURE: yyy

* BUGFIX: xxx
* BUGFIX: yyy
```

Update notes, if any, come first. Then entries are grouped by type in the order `SECURITY`, `FEATURE`, `BUGFIX`, with a blank line between groups.

## Released versions

Released versions use the same groups and order as `tip`, below a version header.

A release candidate has a tag but no release date:

```md
## [v1.156.0](https://github.com/VictoriaMetrics/VictoriaMetrics/releases/tag/v1.156.0)

Release candidate

<!-- same sections and order as in tip -->
```

A released version has a tag and a release date:

```md
## [v1.156.0](https://github.com/VictoriaMetrics/VictoriaMetrics/releases/tag/v1.156.0)

Released at 2026-11-09

<!-- same sections and order as in tip -->
```

An LTS release also has an LTS note after the release date:

```md
## [v1.148.9](https://github.com/VictoriaMetrics/VictoriaMetrics/releases/tag/v1.148.9)

Released at 2026-11-06

**v1.148.x is a line of [LTS releases](https://docs.victoriametrics.com/victoriametrics/lts-releases/). It contains important up-to-date bugfixes for [VictoriaMetrics enterprise](https://docs.victoriametrics.com/victoriametrics/enterprise/).
All these fixes are also included in [the latest community release](https://github.com/VictoriaMetrics/VictoriaMetrics/releases/latest).
The v1.148.x line will be supported for at least 12 months since [v1.148.0](https://docs.victoriametrics.com/victoriametrics/changelog/#v11480) release**

<!-- same sections and order as in tip -->
```

## Security

Security entries describe changes that fix vulnerabilities or reduce exposure to them.

A security entry optionally starts with the affected [components or features](#components-or-features). Upgrades of the Go builder, the base docker image or dependencies affect all components and usually omit them.
Then it describes what was upgraded or fixed. For a fix in VictoriaMetrics code, describe the risk from the user's perspective without details that help exploit it.
It ends with a link to the advisory (GHSA, CVE), release notes, or the related issue/PR/commit.
If the code was contributed by an external contributor, the entry ends with `Thanks to @github_username for the contribution.`

Go builder upgrade:

```md
* SECURITY: upgrade Go builder from Go1.27.3 to Go1.27.4. See [the list of issues addressed in Go1.27.4](https://github.com/golang/go/issues?q=milestone%3AGo1.27.4%20label%3ACherryPickApproved).
```

Base docker image upgrade:

```md
* SECURITY: upgrade base docker image (Alpine) from 3.24.2 to 3.24.3. See [Alpine 3.24.3 release notes](https://www.alpinelinux.org/posts/Alpine-3.21.9-3.22.7-3.23.7-3.24.3-released.html).
```

Dependency upgrade:

```md
* SECURITY: upgrade golang.org/x/net from v0.33.0 to v0.36.0 to address [CVE-2025-22870](https://github.com/advisories/GHSA-qxp5-gwg8-xv66).
```

Fix in VictoriaMetrics code:

```md
* SECURITY: <components or features>: description of the fixed vulnerability. See [GHSA-xxxx-xxxx-xxxx](https://github.com/VictoriaMetrics/VictoriaMetrics/security/advisories/GHSA-xxxx-xxxx-xxxx). Thanks to @github_username for the contribution.
```

The version in the link text must match the version in the entry.

When reviewing a security entry, open every link in it and check that it works and points to the right page: the advisory or CVE exists, the release notes match the upgraded version, and the Go milestone matches the Go version in the entry.
VictoriaMetrics advisories (`https://github.com/VictoriaMetrics/*/security/advisories/GHSA-*`) are usually published only after the release, so they may not open yet. Don't treat such a link as broken; only check that it follows the advisory URL format.

## Features

Features describe new functionality that didn't exist before.

A feature entry starts with the affected [components or features](#components-or-features).
Then it describes how the change works from the user's perspective. It should not be too technical, and ideally links to the appropriate doc section inline.
It ends with a link to the related issue/PR/commit.
If the code was contributed by an external contributor, the entry ends with `Thanks to @github_username for the contribution.`

```md
* FEATURE: <components or features>: description. See [#11384](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/11384). Thanks to @github_username for the contribution.
```

## Bugfixes

Bugfixes fix incorrect behavior of existing functionality.

A bugfix entry starts with the affected [components or features](#components-or-features).
Then it describes the fix from the user's perspective. Ideally, it describes how it worked before and how it works now, so users can tell whether they were affected. It should not be too technical.
It ends with a link to the related issue/PR/commit.
If the code was contributed by an external contributor, the entry ends with `Thanks to @github_username for the contribution.`

```md
* BUGFIX: <components or features>: description of how it works now. Previously, description of how it worked before. See [#11384](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/11384). Thanks to @github_username for the contribution.
```

## Update notes

Update notes warn users about things they must know or do when upgrading to the release. Use them for:

- breaking changes: changed default flag values, new required flags or parameters, removed or renamed flags, metrics, APIs or docker tags, changed API behavior;
- deprecations, e.g. a flag that is deprecated in favor of another one;
- actions required before or after the upgrade, e.g. a config that must be adjusted or components that must be upgraded together;
- known issues found in a release after it was published, e.g. a regression causing memory leaks or failures.

An update note is placed after the version header (and the release date or LTS note), before the `SECURITY`, `FEATURE` and `BUGFIX` entries.
Update notes are numbered sequentially within a release, starting from 1. Only the `**Update Note N:**` label is bold, not the whole note.

An update note optionally starts with the affected [components or features](#components-or-features).
Then it describes what changed and how it affects users. It must tell users what to do: how to keep the previous behavior, what to migrate to, or which version to upgrade or roll back to.
It ends with a link to the related issue/PR/commit.

Breaking change:

```md
**Update Note 1:** <components or features>: the default value of `-flagName` command-line flag has changed from `false` to `true`. Description of how this affects users. If you rely on the previous behavior, pass `-flagName=false`. See [#11384](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/11384).
```

Deprecation:

```md
**Update Note 1:** <components or features>: the `-oldFlag` command-line flag is deprecated. Use `-newFlag` instead. See [#11384](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/11384).
```

Known issue:

```md
**Update Note 1:** <components or features>: description of the issue and its impact. The bug was introduced in [#11000](https://github.com/VictoriaMetrics/VictoriaMetrics/pull/11000). Upgrade to [v1.2.4](https://github.com/VictoriaMetrics/VictoriaMetrics/releases/tag/v1.2.4) or roll back to [v1.2.2](https://github.com/VictoriaMetrics/VictoriaMetrics/releases/tag/v1.2.2). See [#11384](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/11384).
```

## Components or features

Lists the components or features the change relates to. An entry can list several of them. Each component or feature must link to its documentation page.
`FEATURE` and `BUGFIX` entries must list at least one component or feature. Update notes and `SECURITY` entries may omit them, e.g. a Go version upgrade affects all components.
If the change is part of the enterprise offering, prefix the component with `[enterprise](https://docs.victoriametrics.com/victoriametrics/enterprise/)`.

## Examples

```md
**Update Note 1:** `vmctl` in [vm-native](https://docs.victoriametrics.com/victoriametrics/vmctl/victoriametrics/) mode: `--vm-native-filter-time-end` is now a required parameter. See [#11830](https://github.com/VictoriaMetrics/VictoriaMetrics/pull/11830).

* SECURITY: upgrade Go builder from Go1.27.3 to Go1.27.4. See [the list of issues addressed in Go1.27.4](https://github.com/golang/go/issues?q=milestone%3AGo1.27.4%20label%3ACherryPickApproved).
* SECURITY: [vmauth](https://docs.victoriametrics.com/victoriametrics/vmauth/): slow down requests with invalid auth tokens even if `unauthorized_user` has URLs configured. Previously, such requests were proxied to `unauthorized_user` without delay, which allowed brute-forcing auth tokens. See [GHSA-rpfx-hrcp-f73x](https://github.com/VictoriaMetrics/VictoriaMetrics/security/advisories/GHSA-rpfx-hrcp-f73x).

* FEATURE: [vmagent](https://docs.victoriametrics.com/victoriametrics/vmagent/) and [vmsingle](https://docs.victoriametrics.com/victoriametrics/single-server-victoriametrics/): add support for [linode_sd_configs](https://docs.victoriametrics.com/victoriametrics/sd_configs/#linode_sd_configs) for discovering scrape targets from Linode instances. See [#9118](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/9118). Thanks to @cxdy for the contribution.
* FEATURE: [vmagent](https://docs.victoriametrics.com/victoriametrics/vmagent/): add a new flag `-remoteWrite.queuePath`, which allows configuring [persistent-queue](https://docs.victoriametrics.com/victoriametrics/vmagent/#on-disk-persistence) path for each `-remoteWrite.url` independently. See [#11662](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/11662).

* BUGFIX: [vmsingle](https://docs.victoriametrics.com/victoriametrics/single-server-victoriametrics/) and `vmstorage` in [VictoriaMetrics cluster](https://docs.victoriametrics.com/victoriametrics/cluster-victoriametrics/): properly release memory after historical [data backfilling](https://docs.victoriametrics.com/victoriametrics/#backfilling). Previously storage kept 8MiB*CPU memory for each month of ingested data until restart. See [#11672](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/11672). Thanks to @mars71003219 for the contribution.
* BUGFIX: [stream aggregation](https://docs.victoriametrics.com/victoriametrics/stream-aggregation/): properly delay flushes after a sudden ingestion lag spike when [aggregation windows](https://docs.victoriametrics.com/victoriametrics/stream-aggregation/#aggregation-windows) are enabled. Previously, a data gap or a restart could reduce the tolerance for delayed samples to the aggregation interval, resulting in more dropped samples than necessary. See [#11866](https://github.com/VictoriaMetrics/VictoriaMetrics/pull/11866).
```
